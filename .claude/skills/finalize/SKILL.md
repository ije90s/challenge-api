# finalize

`verify`가 끝난 뒤 실제로 커밋하고 작업 기록(워크로그)을 남기는 Skill이다.

## 핵심 원칙

- **이 Skill은 커밋을 막지 않는다 — 그건 이미 `.claude/settings.local.json`의 `permissions.ask` 규칙이 `git commit`을 실행할 때마다 강제로 확인 프롬프트를 띄운다.** 이 Skill이 할 일은 그 프롬프트가 뜨기 전에 무엇을 커밋하려는지 충분히 요약해서 보고하는 것이다. 절대로 그 확인을 텍스트로만 흉내 내고 같은 턴에 넘어가려 하지 마라 — 프롬프트가 실제 게이트다.
- **워크로그 누락도 이미 같은 파일의 Hook이 막는다** (`git commit` 시 당일 `anything/worklog_YYYY-MM-DD.md`가 없으면 차단, `[no-worklog]` 키워드로만 예외). 이 Skill은 그 파일을 제때 작성해서 Hook에 안 걸리게 하는 역할이다.

## 단계

### 1. 코드 커밋
- 지금까지의 분석/구현/검증 결과를 사용자에게 간단히 요약 보고한다 (무엇을 왜 바꿨는지, 테스트/빌드/리뷰 결과).
- `git add`는 이번 작업의 diff에 정확히 대응하는 파일만 명시적으로 지정한다 (`-A` 금지).
- `git commit`을 실행한다 — **이때 harness가 확인 프롬프트를 띄운다.** 사용자가 승인하면 커밋되고, 거절하면 여기서 멈춘다. 같은 턴에서 이 결과를 우회하거나 재시도하지 않는다.

### 2. 워크로그 작성
`anything/worklog_YYYY-MM-DD.md`에 이번 작업을 정리해서 추가한다 (기존 파일 형식 참고: 분석&질문 → 변경사항 요약 표 + 커밋 해시 → 검증 결과 → 예외사항/남겨둔 것). **코드 커밋과는 별도의 커밋으로 처리한다.**

### 3. 워크로그 커밋
워크로그 파일만 `git add`한 뒤 `git commit`을 실행한다 — 이것도 동일한 확인 프롬프트가 뜬다.

## 다음 단계

이 Skill로 하나의 작업 단위가 마무리된다. 같은 세션에서 이어서 다른 TODO를 처리한다면 `todo`부터 다시 시작한다 (서로 다른 작업의 변경사항을 하나의 diff/커밋으로 합치지 않는다).
