# todo

`challenge-api` 리포지토리에서 "무엇을 해야 하는지"를 작업 단위로 정의/분해하는 Skill이다. 리팩토링뿐 아니라 기능 개발, 버그 수정, 부하 테스트 등 어떤 작업 종류에도 동일하게 쓴다. **이 단계에서는 소스 코드(`src/`, `test/` 등)를 수정하지 않는다** — 수정 대상은 TODO 문서 자체뿐이다.

기본 TODO 소스 문서는 `anything/refactor_plan.md`다. 다른 문서를 다뤄야 하면 `$ARGUMENTS`로 경로를 지정한다.

## 모드 판단

`$ARGUMENTS` 또는 사용자 발화로 다음 중 어느 모드인지 먼저 판단한다.

- 사용자가 "이런 걸 해야 한다"고 새로운 목표/요구사항을 던졌고, TODO 문서에 아직 그 항목이 없다 → **작성 모드**
- TODO 문서에 이미 미완료 항목들이 있고, 그중 하나를 처리하려 한다 → **선택 모드**
- 둘 다 해당할 수도 있다 (새 항목을 몇 개 추가한 뒤 그중 하나를 바로 선택) — 이 경우 작성 → 선택 순서로 진행한다.

## 작성 모드

1. 사용자가 말한 목표/요구사항을 관련 코드를 깊게 조사하지 않는 선에서(깊은 코드 분석은 `analyze` Skill의 몫) 작업 단위로 분해한다. 너무 크면 나누고, 너무 잘게 쪼개서 관리 부담을 늘리지 않는다.
2. 대상 문서의 기존 구조(예: `refactor_plan.md`의 Phase 구성, 체크박스 리스트 형식)를 그대로 따라 새 항목을 추가한다.
3. 새 항목이 기존 우선순위 구조(Phase 등) 어디에 들어가야 할지 애매하면, 하드 게이트까지는 아니더라도 사용자에게 가볍게 확인한다 ("이건 Phase N에 넣을까요, 별도로 둘까요?" 수준). 명확하면 확인 없이 바로 추가하고 어디에 넣었는지만 통지한다.
4. 추가한 항목을 한 문장씩 사용자에게 요약 보고한다.

## 선택 모드

1. 대상 TODO 문서를 읽는다.
2. `$ARGUMENTS`로 특정 항목이 지정됐으면 그 항목을, 아니면 문서에서 아직 처리되지 않은 다음 항목을 찾는다.
3. 어떤 항목을 처리할지 한 문장으로 사용자에게 알린다. **이 확인은 게이트가 아니다** — 바로 다음 단계(`analyze`)로 넘어가면 된다.
