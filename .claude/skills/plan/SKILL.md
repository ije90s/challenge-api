# plan

`analyze` 결과를 바탕으로 "어떻게 해결할 것인가"를 결정하는 Skill이다. **이 Skill이 Analyze → Execute 사이의 핵심 의사결정 게이트다** — 여기를 통과하지 않고 코드를 수정하면 안 된다.

## 핵심 원칙

- **AI가 임의로 설계 판단을 내리지 않는다.** 선택지가 있는 지점(필드 범위, 여러 구현 방식 중 선택, 파일/모듈 위치, 스코프 경계 등)은 반드시 `AskUserQuestion`으로 사용자에게 묻는다. 답을 추측해서 진행하지 않는다.
- 설계 갈림길이 없고 구현 방향이 명확하면, "설계 판단 불필요, 이대로 진행합니다"라고 짧게 밝히고 게이트 없이 넘어갈 수 있다 — 매 항목마다 형식적으로 확인받을 필요는 없다.
- **사용자의 승인 전에는 실제 코드 수정(Edit/Write)으로 넘어가지 않는다.** 이 Skill 자체도 코드를 수정하지 않는다 — 제안과 합의까지만이 책임이다.
- 제안하는 범위는 `analyze`에서 확인된 문제에 대응하는 만큼으로 한정한다. 범위를 넘어서는 리팩토링/추상화/정리를 미리 계획에 끼워넣지 않는다.

## 단계

1. `analyze` 결과의 `Open Questions`와 `Findings`를 바탕으로 가능한 구현 방법(들)을 정리한다.
2. 방법이 여러 개거나 트레이드오프가 있으면 `AskUserQuestion`으로 선택지를 제시하고 답을 받는다.
3. 확정된 방법을 다음을 포함해 요약 보고한다: 변경 범위(건드릴 파일/모듈), 접근 방식, 범위에서 명시적으로 제외한 것.
4. 요약 보고 후, **항상 "이대로 구현을 진행해도 될까요?"처럼 명시적으로 구현 진입 승인을 받는다** — 설계 갈림길에서 `AskUserQuestion`에 답한 것 자체를 승인으로 간주하지 않는다(설계 선택과 구현 착수는 별개의 확인). 사용자가 승인해야 다음 단계로 넘어간다.

## 다음 단계

승인 후에는 합의된 범위로만 실제 구현을 진행한다 (별도 Skill 없이 바로 Edit/Write). 구현이 끝나면 `verify` Skill로 넘어간다.
