# analyze

`todo` 단계에서 확정된 작업 단위(또는 사용자가 직접 지정한 조사 대상)에 대해 관련 코드, 구조, 요구사항, 영향 범위를 조사해서 보고하는 Skill이다. 리팩토링/기능개발/버그수정/부하테스트 등 작업 종류와 무관하게 동일하게 쓴다.

## 핵심 원칙

- **이 단계에서 Edit/Write를 호출하지 않는다.** 조사와 보고만 한다.
- **구현 방법을 임의로 확정하지 않는다.** "어떻게 해결할 것인가"는 `plan` Skill의 책임이다 — 여기서는 "무엇이 문제인가"만 다룬다.
- 확인하지 않은 내용을 사실처럼 쓰지 않는다. 파일을 확인했으면 가능한 한 `파일 경로`와 코드 위치(줄 번호 등)를 함께 명시한다.
- 추측이 필요한 부분은 사실과 명확히 구분해서 표시한다.

## 출력 형식 (고정 — 순서/제목 변경 금지)

분석 결과는 항상 아래 형식으로만 출력한다. 해당 내용이 없는 섹션은 삭제하지 않고 `없음`이라고 표시한다.

```markdown
## Analysis

### 1. Task
- 현재 작업의 목적을 한 문장으로 정리

### 2. Current State
- 현재 코드/구조가 어떻게 동작하는지 설명
- 관련 파일과 주요 코드 위치를 명시

### 3. Problem
- 현재 문제 또는 변경이 필요한 이유
- 확인된 문제만 작성하고 추측은 구분해서 표시

### 4. Impact
- 변경 시 영향을 받을 수 있는 코드/기능
- 관련 의존성 및 데이터 흐름

### 5. Constraints
- 기존 코드에서 반드시 유지해야 하는 조건
- 프로젝트 규칙, 기술적 제약, 호환성 등

### 6. Findings
- 분석을 통해 확인한 핵심 사실을 정리
- 사실과 추론을 명확하게 구분

### 7. Open Questions
- 현재 분석만으로 결정할 수 없는 사항
- 사용자의 판단이 필요한 사항
- 질문이 없다면 `없음`으로 표시

### 8. Summary
- 현재 상태와 핵심 문제를 3~5줄로 요약
- 아직 구현 방법이나 변경 계획을 확정하지 않는다.
```

`Open Questions`는 사용자의 판단이 실제로 필요한 경우에만 채운다 — 형식적으로 질문을 만들어내지 않는다.
