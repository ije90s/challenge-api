# refactor-todo

이 리포지토리(`challenge-api`)에서 `anything/refactor_plan.md`의 TODO 항목을 하나 처리할 때 사용하는 고정 워크플로우다. `$ARGUMENTS`로 특정 TODO를 지정할 수 있고, 없으면 refactor_plan.md에서 아직 처리되지 않은 다음 항목을 찾는다.

## 핵심 원칙 (모든 단계에 우선한다)

- **AI가 임의로 설계 판단을 내리지 않는다.** 선택지가 있는 지점은 반드시 사용자에게 묻는다.
- **분석과 구현을 분리한다.** 분석 단계에서는 코드를 수정하지 않는다.
- **AI_VERIFIED ≠ USER_VERIFIED.** 테스트/빌드/코드리뷰가 통과했다는 것과 "이 작업이 끝났다"는 것은 다르다. 최종 판단(커밋)은 사용자가 한다.
- **이 스킬은 커밋을 막지 않는다 — 그건 이미 `.claude/settings.local.json`의 `permissions.ask` 규칙이 `git commit`을 실행할 때마다 강제로 확인 프롬프트를 띄운다.** 이 스킬이 할 일은 그 프롬프트가 뜨기 전에 무엇을 커밋하려는지 충분히 요약해서 보고하는 것이다. 절대로 그 확인을 텍스트로만 흉내 내고 같은 턴에 넘어가려 하지 마라 — 프롬프트가 실제 게이트다.
- **워크로그 누락도 이미 같은 파일의 Hook이 막는다** (`git commit` 시 당일 `anything/worklog_YYYY-MM-DD.md`가 없으면 차단, `[no-worklog]` 키워드로만 예외). 이 스킬은 그 파일을 제때 작성해서 Hook에 안 걸리게 하는 역할이다.

## 단계

### 1. 투두리스트 확인
`anything/refactor_plan.md`를 읽고 `$ARGUMENTS`로 지정된 항목, 또는 다음으로 처리할 미완료 항목을 확인한다. 어떤 항목을 처리할지 한 문장으로 사용자에게 알린다. (여기는 게이트 아님 — 확인만 하고 바로 진행)

### 2. 분석 (ANALYZE) — 수정 금지
관련 파일, 현재 구조, 문제점, 영향 범위를 조사해서 보고한다. **이 단계에서 Edit/Write를 호출하지 않는다.**

### 3. 검토 & 질문 (QUESTION / DESIGN REVIEW) — 설계 갈림길이 있을 때만 하드 게이트
분석 결과 설계 판단이 필요한 지점(필드 범위, 타입 vs DTO 분류, 폴더 위치, 여러 구현 방식 중 선택 등)이 있으면 **`AskUserQuestion`으로 반드시 물어본다.** 답을 추측해서 진행하지 않는다.

설계 갈림길이 없고 구현 방향이 명확하면 ("설계 판단 불필요, 이대로 진행합니다"라고 짧게 밝히고) 게이트 없이 다음 단계로 넘어간다 — 매 항목마다 형식적으로 확인받을 필요는 없다는 게 기존에 확정된 방침이다.

### 4. 수정 (IMPLEMENT)
2/3단계에서 합의된 범위로만 구현한다. 범위를 넘어서는 리팩토링/추상화/정리는 하지 않는다.

### 5. diff 범위 확인
`git diff --stat` (또는 동등한 명령)을 바로 실행해서, 의도하지 않은 파일 변경(예: 포맷터가 무관한 파일을 건드린 경우)을 조기에 발견한다. 이상하면 여기서 멈추고 원인을 밝힌다.

### 6. 테스트 & 빌드
프로젝트의 유닛 테스트와 빌드를 실행해서 회귀가 없는지 확인한다.

### 7. 코드리뷰
`/code-review`를 실행한다. 결과를 맹신하지 말고 직접 검증한다 — 과거에 리뷰가 틀린 주장을 한 적이 있다(컴파일 테스트로 반증됨). 확신이 안 서면 실제로 확인해본다.

### 8. 커밋
- 지금까지의 분석/구현/검증 결과를 사용자에게 간단히 요약 보고한다 (무엇을 왜 바꿨는지, 테스트/빌드/리뷰 결과).
- `git add`는 이번 항목의 diff에 정확히 대응하는 파일만 명시적으로 지정한다 (`-A` 금지).
- `git commit`을 실행한다 — **이때 harness가 확인 프롬프트를 띄운다.** 사용자가 승인하면 커밋되고, 거절하면 여기서 멈춘다. 같은 턴에서 이 결과를 우회하거나 재시도하지 않는다.

### 9. 워크로그 작성
`anything/worklog_YYYY-MM-DD.md`에 이번 항목을 정리해서 추가한다 (기존 파일 형식 참고: 분석&질문 → 변경사항 요약 표 + 커밋 해시 → 검증 결과 → 예외사항/남겨둔 것). **코드 커밋과는 별도의 커밋으로 처리한다.**

### 10. 워크로그 커밋
워크로그 파일만 `git add`한 뒤 `git commit`을 실행한다 — 이것도 동일한 확인 프롬프트가 뜬다.

## TODO 처리 단위

같은 세션에서 여러 TODO를 이어서 처리하더라도, 항목마다 1~10단계를 독립적으로 처음부터 다시 실행한다. 서로 다른 TODO의 변경사항을 하나의 diff/커밋으로 합치지 않는다 — 항목별로 코드 커밋 1개 + 워크로그 커밋 1개가 원칙이다.
