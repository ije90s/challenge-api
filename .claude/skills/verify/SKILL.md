# verify

`plan`에서 합의된 대로 구현이 끝난 뒤, 변경 결과가 의도대로 동작하는지 검증하는 Skill이다. 작업 종류(기능개발/버그수정/리팩토링/부하테스트)에 따라 구체적인 검증 방법은 달라질 수 있지만 절차는 동일하다.

## 핵심 원칙

- **AI_VERIFIED ≠ USER_VERIFIED.** 테스트/빌드/코드리뷰가 통과했다는 것과 "이 작업이 끝났다"는 것은 다르다. 최종 판단은 `finalize` 단계의 커밋에서 사용자가 한다.
- Verify와 Code Review는 구분한다 — Verify는 동작/품질(빌드가 되는지, 테스트가 통과하는지, 성능 목표를 만족하는지)을 확인하고, Code Review는 코드 자체의 설계/품질/누락을 검토한다.

## 단계

### 1. diff 범위 확인
`git diff --stat`(또는 동등한 명령)을 바로 실행해서, 의도하지 않은 파일 변경(예: 포맷터가 무관한 파일을 건드린 경우)을 조기에 발견한다. 이상하면 여기서 멈추고 원인을 밝힌다.

### 2. 테스트 & 빌드
프로젝트의 유닛 테스트(`npm test`)와 빌드(`npm run build`)를 실행해서 회귀가 없는지 확인한다. 관련 변경이면 e2e(`npm run test:e2e`)도 고려한다. 변경이 소스 코드에 영향이 없는 문서 전용 작업이면 이 단계를 생략하되 생략 사유를 사용자에게 밝힌다.

### 3. 부하 테스트 (해당하는 경우만)
성능/부하 관련 작업이면 이 단계에서 부하 테스트 스크립트 실행 및 실측(예: k6)을 수행한다. 해당하지 않으면 건너뛴다.

### 4. 코드리뷰
`/code-review`를 실행한다. **결과를 맹신하지 말고 직접 검증한다** — 과거에 리뷰가 틀린 주장을 한 적이 있다(컴파일/테스트로 반증된 사례 있음). 확신이 안 서면 실제로 코드를 확인하거나 재현해본다.

## 다음 단계

테스트/빌드/코드리뷰가 모두 정리되면 `finalize` Skill로 넘어가 커밋과 워크로그를 진행한다.
