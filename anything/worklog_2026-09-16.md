# 2026-09-16 워크로그

## Phase 4 — `ParticipationService.create`의 중복 참가 check-then-act race 최종 해결

### 분석 & 질문

- `refactor_plan.md` Phase 4의 마지막 미체크 TODO("`ParticipationService.create`의 중복 참가 check-then-act race 검토")를 처리 대상으로 확인 — 2026-09-15 score/challenge_count 원자성 분석 중 발견해 별도 항목으로 분리해뒀던 것.
- `analyze` 단계에서 `findOne`(사전 체크) → `create`+`save`(삽입) 사이에 원자성이 없고, `participation` 테이블에 `(user_id, challenge_id)` DB 레벨 유니크 제약이 없음을 마이그레이션 파일(`1766221023728-Init.ts`, `1766475886412-ModifyChallengeFK.ts`) 직접 확인으로 재검증. 같은 프로젝트의 `Challenge.title`/`Feed.title`은 이미 DB 유니크 제약으로 중복을 막는 선례가 있음을 확인.
- `plan` 단계에서 두 갈림길을 `AskUserQuestion`으로 확인:
  - 해결 방식: **DB 복합 유니크 인덱스 + 중복키 에러 캐치**(비관적 락 대비 title 컬럼과 컨벤션 일치, 구현 단순) 선택.
  - 검증 방식: **e2e `Promise.all` 동시 요청 테스트**(k6 인프라 없이 재현 가능) 선택.
- 마이그레이션 실행 전 로컬 DB를 직접 조회해 `(user_id, challenge_id)`가 non-null인 기존 중복 로우가 없음을 확인(부하 테스트 잔여 데이터는 `user_id IS NULL`이라 무관) — 안전하게 적용 가능함을 미리 검증.
- `migration:generate`가 이번 변경과 무관한 기존 스키마 drift(예: `feed.images` 컬럼 타입, FK 제약명 등, MariaDB의 `json`→`longtext+check` 내부 표현 차이로 인한 것으로 추정)까지 포함시켜서, 유니크 인덱스 추가 한 줄만 담도록 마이그레이션 파일을 수동으로 다시 작성.

### 코드리뷰에서 발견해 함께 수정한 것

`/code-review` 실행 결과 7건 지적, 직접 재현/검증 후 판단:

- **바로 수정(이번 diff 내 하드닝)**:
  - 중복키 판별이 `error`에 대한 unsafe cast(`error.code`, 비공식으로 복사된 속성에 의존)였던 것을 → TypeORM이 공식으로 노출하는 `error.driverError`로 교체.
  - `ER_DUP_ENTRY`만 보고 무조건 매칭하던 것을 → `driverError.sqlMessage`에 `idx_unique_user_challenge`가 포함된 경우로 한정. 실제 MariaDB 에러 메시지 형식(`Duplicate entry '1-2' for key 'idx_unique_user_challenge'`)을 로컬 DB에 수동 INSERT로 직접 재현해 확인.
  - `"이미 참가중입니다."` 리터럴 중복 기재를 상수로 추출.
- **별도 TODO로 분리(다른 모듈의 기존 버그, 이번 범위 밖)**:
  - `UserService.signUp()`의 이메일 중복가입 check-then-act 레이스(같은 구조, 미보호).
  - `Challenge.title`/`Feed.title` 생성 시 동일 계열 중복 제목 레이스(같은 구조, 미보호).
- **기록만 남기고 범위 제외**:
  - "새 유니크 인덱스가 soft-delete를 고려하지 않아, 참가 취소를 soft-delete로 구현하면 재참가가 영구히 막힐 수 있다" — 현재 `Participation`엔 soft-delete를 호출하는 코드가 전혀 없어(참가 취소 기능 미구현) 재현 불가능한 잠재 버그. 사용자와 논의 결과 hard-delete 전환은 선택지가 아님(이 프로젝트가 soft-delete를 쓰는 이유 자체가 로우 증가 시 영구 삭제 회피)을 확인, 향후 해결 후보로 (a) 생성 컬럼 트릭, (b) 재참가 시 `restore()` 패턴을 논의해 `refactor_plan.md`에 기록.
  - 마이그레이션에 사전 중복 데이터 정리 스텝이 없다는 지적은 실행 전 로컬 DB에 중복이 없음을 이미 확인했으므로 변경 불필요로 판단.
