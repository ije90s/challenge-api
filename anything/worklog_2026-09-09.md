## 1. 분석 & 질문

### 분석

**컨트롤러 스펙 최소 계약 테스트**
- `challenge/feed/participation/user.controller.spec.ts` 4개 파일 모두 `should be defined`만 있는 트리비얼 테스트였음.
- NestJS의 `Test.createTestingModule().compile()` 방식 유닛 테스트는 컨트롤러 인스턴스만 생성할 뿐 Guard/Pipe/Interceptor는 실행되지 않음 — 실제 Nest 애플리케이션(`createNestApplication()` + supertest)을 띄워야만 동작.
- `test/app.e2e-spec.ts`(09-08에 격리 도입 완료)가 이미 User/Challenge/Participation/Feed 전 도메인에서 "토큰 없는 경우"/"잘못된 토큰인 경우"(Guard 차단)와 "필수값이 없는 경우"/"파라미터 타입 확인"(400)을 실제 HTTP 요청으로 촘촘히 검증 중 — 원래 refactor_plan에서 지적한 "컨트롤러 레벨 가드/400 미검증" 문제는 이미 해소된 상태.

**1-1~1-3 회귀 테스트 갭**
- 커밋별로 테스트 변경 여부를 대조해 4곳의 갭을 확인:
  - `JwtStrategy.validate()` await 누락 수정(`3e0aa10`) — `jwt.strategy.spec.ts` 자체가 없어 커버리지 0
  - `MulterExceptionFilter` 이중 응답 정리(`6e23d24`) — `multer.exception.filter.spec.ts` 없음
  - `challenge.author`/`feed.user` null 가드(`fcabc0a`) — `challenge.service.spec.ts`에 `author: null` 케이스 없음, `feed.service.spec.ts`도 손대긴 했지만(28줄) `user: null` 케이스는 없음
  - `UpdateParticipationDto`의 `@Min(0)` 음수 검증(`c8472fe`) — 유닛/e2e 어디에도 음수값 테스트 없음

### 질문과 결론
- **"컨트롤러 스펙에 뭘 추가할까요? (reflection 기반 최소 검증 / supertest 기반 통합 테스트 / e2e로 충분하니 스킵)"** → **reflection 기반 최소 검증**으로 결정. e2e가 이미 실 HTTP로 충분히 커버하는 상태에서 supertest 기반 통합 테스트를 새로 만드는 건 중복 비용 대비 실익이 적음. 대신 "guard 데코레이터가 실수로 빠지면 컴파일 없이 즉시 잡아주는" 가벼운 검증은 저비용이라 채택.
- **"회귀 테스트 갭 4곳을 다 채울까요, 핵심 로직 버그(null 가드/음수 검증)만 할까요?"** → **4곳 전부** 진행하기로 결정. jwt await/multer 이중응답은 "우연히 동작하던 취약한 코드"를 고친 케이스라 회귀 테스트 없이는 나중에 되돌려져도 아무도 못 잡는다는 이유.

## 3. 검증 결과

- `npm test` → 12 suites / 88 tests 전부 통과
- `npm run test:e2e` → 55/55 통과 (신규 음수값 케이스 2건 포함)
- `npm run build` → 성공
- `/code-review` 스킬로 diff 리뷰 실행 → 3건 발견, 검증 후 1건 수정 · 2건은 스코프 밖으로 판단:
  1. **수정** — `GUARDS_METADATA` reflection 검증 로직이 4개 스펙 파일에 그대로 복붙됨 → `src/common/test/guard-metadata.helper.ts` 공유 헬퍼로 통합.
  2. **스코프 밖** — "Phase 2에서 `JwtAuthGuard`를 `APP_GUARD`로 옮기면 이 reflection 테스트들이 깨질 수 있다"는 지적 → 맞는 말이지만 이번에 선택한 "reflection 최소 검증" 방식 자체의 트레이드오프이므로 되돌리지 않고 Phase 2 진행 시 참고할 사항으로만 남김.
  3. **스코프 밖** — e2e 음수값 테스트 2건을 `it.each`로 합치라는 지적 → `test/app.e2e-spec.ts` 전체(55개 테스트)가 이미 일관되게 "매 `it`마다 자체 `beforeEach` fixture" 패턴이고 `it.each`를 쓰는 곳이 한 군데도 없어, 여기만 다른 스타일을 넣으면 오히려 일관성이 깨진다고 판단.
- 리뷰에서 직접 잡히지 않았지만 자체 lint 확인 중 발견: `getGuards(UserController.prototype.signUp)`처럼 클래스 메서드를 호출 없이 참조로 넘기는 패턴이 `@typescript-eslint/unbound-method` 경고를 유발 → 실제 호출이 아니라 메타데이터 조회 대상으로만 쓰는 의도된 패턴이라 `eslint-disable-next-line` 주석으로 처리(사유 코멘트 포함).
- `npx eslint`로 변경/신규 파일 개별 확인 — 남은 경고 대부분은 리포 전체에 퍼진 기존 4-space/2-space prettier 컨벤션 불일치(HEAD 상태에서도 동일하게 발생, `git stash`로 대조 확인)라 손대지 않음. `participation.controller.spec.ts`의 `ChallengeModule` 미사용 import도 이번 변경 이전부터 있던 것이라 그대로 둠.

## 4. 예외 사항 / 남겨둔 것

- 컨트롤러 스펙의 guard 검증은 reflection 기반이라, Phase 2(모듈/인증 가드 구조 정리)에서 `JwtAuthGuard` 적용 방식을 클래스 데코레이터에서 `APP_GUARD` 등으로 바꾸면 이 테스트들이 깨질 수 있음 — Phase 2 착수 시 함께 갱신 필요.
- 리포 전체의 prettier 스타일 불일치(`npm run format` 전체 실행 시 대량 diff 발생)는 이번 스코프에서 손대지 않음, `[[feedback_prettier_scope]]` 메모 기존 방침 유지.
- Phase 1 전체 완료. 다음은 Phase 2(인증 정책 재검토, `User ↔ Auth` `forwardRef` 순환 의존 재검토).
