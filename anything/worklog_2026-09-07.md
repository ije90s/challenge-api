### null 가드 분석
- **근본 원인**: `Challenge.author`, `Feed.user`/`challenge`, `Participation.user`/`challenge`가 전부 `@ManyToOne(..., { onDelete: 'SET NULL' })`인데, 엔티티 타입은 non-null(`User`, `Challenge`)로 선언되어 있어 컴파일러가 null 케이스를 못 잡음.
- grep으로 실제 `.id` 역참조 지점을 전수 확인 → 정확히 4곳: `response-challenge.dto.ts:21`, `response-feed.dto.ts:16-17`, `challenge.service.ts`의 update/delete(83, 116행), `feed.service.ts`의 update/delete(103, 127행). `Participation`은 서비스/DTO 어디서도 `.user.id`/`.challenge.id`를 직접 읽지 않아 실제 크래시 지점 없음(타입만 부정확).
- **실제 트리거 가능성 확인**: `UserService`에 삭제 로직 자체가 없고, `Challenge`/`Feed` 삭제도 `softDelete()`만 사용(물리 삭제 아님) → `onDelete: 'SET NULL'`은 물리 DELETE에서만 발동하므로, 현재 API 경로로는 이 null 상태가 절대 만들어지지 않음. 회원 탈퇴(하드 삭제) 기능이 추후 추가될 때를 대비한 선제적 수정으로 성격을 규정.
- 사용자가 짚은 두 가지 오해를 정정하며 논의:
  - "TypeORM이 조회 시 null 관계는 배제하는 거 아닌가?" → 아니다. `relations: [...]`는 LEFT JOIN이라 관계값이 null이어도 원본 row는 그대로 반환됨. `deleted_at IS NULL` 같은 명시적 `where` 조건만 자동 필터링됨.
  - "null !== userId로 자동으로 권한 비교가 막히는 거 아닌가?" → 의도한 최종 동작(작성자 없으면 아무도 접근 불가)은 맞지만, JS는 `null.id`를 `undefined`로 조용히 넘기지 않고 그 자리에서 `TypeError`를 던져 비교문 자체에 도달하지 못함. `?.`/`!x ||` 형태의 명시적 가드가 필요.
- **해결 방향 확정**: 엔티티 타입을 `T | null`로 정정해 TypeScript가 4개 지점을 컴파일 에러로 강제 검출하게 하고, 각 지점에 옵셔널 체이닝/가드 추가. DTO도 응답 계약(API contract) 관점에서 nullable로 맞춤(프론트엔드가 "작성자 없음" 케이스를 인지할 수 있어야 함).
- `ParticipationService.update`의 score/challenge_count 원자적 처리는 계획서 자체에 "실제 반영은 Phase 4와 함께 재검토"로 명시되어 있어 이번엔 검토만 하고 코드 변경은 보류.

## 5. `ParticipationService.update` score/challenge_count 원자적 처리 검토

### 분석
- `findOne`으로 읽고(①) 메모리에서 `score`/`challenge_count`를 더한 뒤(②) `save()`로 통째로 덮어쓰는(③) read-modify-write 패턴. 트랜잭션/락/원자적 SQL 연산(`increment()`) 전부 없음 — 저장소 전체에 `transaction`, `VersionColumn`, `increment(`, `pessimistic`/`optimistic` 키워드가 하나도 없음을 grep으로 확인.
- **Lost update 재현**: 초기 `score=5`일 때 두 요청이 거의 동시에 각각 `+3`, `+2`를 보내면, TypeORM `save()`가 SQL 증분이 아니라 JS 객체 값 그대로 덮어쓰기 때문에 나중에 커밋된 쪽이 먼저 커밋된 값을 통째로 덮어씀 — 최종값이 `7`이 되어 정답(`10`)보다 작아짐(+3 유실).
- **부수 문제**: `status`(완료 처리) 판정도 자신이 읽은 stale한 `participation.score` 기준 `total`로 계산하므로, 동시 요청 시 개별로는 `mininum_count`를 못 넘어도 순차 처리였다면 넘었을 케이스를 완료 처리로 놓칠 수 있음(숫자 유실뿐 아니라 도달 판정 정합성 문제).
- **실제 트리거 가능성**: 동일 유저가 동일 `(challengeId, userId)`에 거의 동시에 여러 요청을 보내야 발생 — 버튼 연타/재시도/다중 기기에서 가능하고, 무엇보다 계획서 Phase 4에 "동시 참가/기록 갱신"이 이미 부하 테스트 시나리오로 명시되어 있어 그 단계에서 의도적으로 재현·측정하게 됨.
- **선택지(적용 안 함)**: (1) `repository.increment()`로 숫자 증분만 원자화 — 단 완료 판정은 증분 후 값을 다시 읽어야 함, (2) 비관적 락(`SELECT ... FOR UPDATE`, 트랜잭션) — 정확하지만 동시 요청 몰릴 때 대기/처리량 저하 가능, (3) 낙관적 락(`@VersionColumn`) — 대기는 없지만 충돌 시 재시도 로직 필요. 세 선택지의 우열은 부하 테스트 실측(충돌 빈도, 락 경합 정도) 없이는 판단 근거가 없음.
- **곁다리 발견**: `UpdateParticipationDto.score`/`challenge_count`에 하한 검증이 없어 음수 값도 통과 — 원자성 문제와 무관한 별개 결함이라 이번에 같이 반영.

### 결정
- 원자적 처리 방식 선택은 Phase 4 부하 테스트("동시 참가/기록 갱신" 시나리오) 실측 후 재검토로 확정 — `refactor_plan.md` Phase 4에 이미 있던 "score/challenge_count 원자적 갱신 여부 최종 결정 (실측 기반)" 항목과 동일 선상이라 별도 항목 추가 없이 그대로 연결.
- 검토 중 발견한 음수값 미검증 문제만 이번에 바로 수정.

## 6. `findByTitle` sentinel 제거 + DataSource 통합 보류 결정

### `findByTitle(id, title)` → `findByTitle(title, excludeId?)`
- `create()`에서 자기 자신을 제외할 ID가 없어 존재할 수 없는 sentinel(0)을 넘겨 "제외 없음"을 흉내내던 방식 제거. `excludeId`를 옵셔널로 바꾸고, 있을 때만 `where`에 `id: Not(excludeId)`를 조건부로 추가.
- 사용자 확인 질문: "조건절에 예외적인 걸 빼고 조회하는 거냐?" → 그렇다. `create()` 호출(`findByTitle(title)`)은 이제 아예 id 제외 조건 없이 전체에서 제목 중복만 확인하고, `update()` 호출(`findByTitle(dto.title, challengeId)`)만 본인 제외 조건이 붙음 — sentinel(0)으로 우연히 동작하던 것과 결과는 같지만 의도가 코드에 드러남.
- 변경 범위: `challenge.service.ts`/`feed.service.ts`의 `findByTitle` 정의 + `create`/`update` 호출부(각 2곳), 그리고 스펙에서 `findByTitle(id, title)` 형태로 직접 호출하던 4곳(`challenge.service.spec.ts` 136, 146행 / `feed.service.spec.ts` 125, 136행)의 인자 순서 수정. `jest.spyOn(...).mockResolvedValue(...)` 형태로 쓰인 나머지 테스트는 인자 순서와 무관해 영향 없음(사전 grep으로 `findByTitle` 호출 인자를 검증하는 assertion이 없음을 확인).

### DataSource 통합 — 진행 안 함
- 제안 검토 중, 작성자가 "일부러 `typeorm.datasource.ts`는 마이그레이션 CLI 전용, `app.module.ts`는 런타임 앱 전용으로 분리해서 마이그레이션이 어떻게 동작하는지 관찰하려고 지금 상태로 둔 것"이라고 확인 — 이번 계획에서 통합 작업 자체를 보류하기로 결정.
- 확인 과정에서 사용자의 "dev는 datasource.ts가 서빙, prod는 app.module.ts가 서빙" 가설을 실제 코드로 검증 → 사실이 아님을 확인: `typeorm.datasource.ts`는 `typeorm:d` CLI 스크립트에서만 로드되고 런타임 앱은 dev/prod 구분 없이 항상 `app.module.ts`만 사용. `package.json`의 `start:dev`/`start:prod` 어디에도 `.env.dev`/`.env.prod`를 갈아 끼우는 로직(`dotenv -e`, `cross-env` 등)이 없어, 두 파일의 실질적 차이는 "dev vs prod"가 아니라 "런타임 앱 vs CLI 마이그레이션 도구"임을 확인. 이 사실 확인 후에도 사용자는 통합하지 않고 그대로 두기로 결정(마이그레이션 동작 관찰 목적).
- 커넥션 자격증명 리터럴(host/port/user/pass/db) 중복 자체는 여전히 존재하지만, 실질적 위험(dev/prod 오분기 등)이 없다는 게 확인된 상태이므로 `refactor_plan.md`에 "진행 안 함(의도적 보류)"으로 기록.
