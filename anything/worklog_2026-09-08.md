# Part 1 — `FeedService.update` 이미지 유실 버그 수정

---

## 1. 분석 & 질문

### 분석
- `feed.service.ts:113` (수정 전): `dto.images = this.getFileArr(images) ?? feed.images;`
- `getFileArr()`(`feed.service.ts:20-28`)는 `images`가 `undefined`/`[]`여도 항상 `string[]`을 반환 — `if(images)` 가드 안에서 `.map`하고, 아니면 초기값 `[]` 그대로 리턴. 즉 반환값이 `null`/`undefined`가 될 수 없어 `?? feed.images` fallback은 절대 실행되지 않는 죽은 코드.
- 실제 영향: 사용자가 새 이미지 첨부 없이 제목/내용만 수정하면(`FeedController.updateFeed`의 `FilesInterceptor`가 빈 배열/undefined를 넘김) `dto.images`가 `[]`로 덮어써져 기존 업로드 이미지가 전부 유실됨.
- `feed.service.spec.ts`의 기존 "피드 수정" 테스트(update describe 블록)는 새 이미지를 첨부하는 케이스만 검증하고 있어 이 회귀를 못 잡고 있었음.
- 연관 확인: `UpdateFeedDto`는 `PickType(CreateFeedDto, ['title','content','images'])`이라 `images`는 여전히 `@IsOptional()` — DTO 설계 자체는 문제 없고, 서비스 로직이 "새 이미지 안 왔음"과 "빈 배열로 비우고 싶음"을 구분 못 하는 게 원인.

### 질문과 결론
- **"images 미첨부 시 기존 이미지를 유지하는 걸로 고친다면, '이미지를 전부 지우고 싶다'는 케이스는 이번 스코프에 넣을까요?"** → 넣지 않기로 결정. 새 이미지 없으면 무조건 기존 유지만 처리(스코프 최소화). 전체 삭제 기능은 별도 파라미터/플래그가 필요한 범위 확장이라 이번 버그 수정에서는 제외.

# Part 2 — Phase 1-4 첫 항목: e2e 테스트 격리 전략 도입

## 1. 분석 & 질문

### 분석
- `test/app.e2e-spec.ts`(621줄)가 별도 테스트 DB 없이 `.env`(`DB_NAME=challenge`, 로컬 Docker MariaDB)에 직접 접속해서 실행되고 있었음 — `AppModule`이 `ConfigModule.forRoot({isGlobal:true})`로 기본 `.env`를 로드하고, `test:e2e` 스크립트도 별도 env 분기가 없음.
- 그 결과 스펙 곳곳이 "과거 한 번 실행되어 이미 만들어진 DB 상태"를 전제로 짜여 있었음: "회원가입 성공/중복"은 원래 `.expect(201)`이었던 게 주석 처리되고 `.expect(409)`(이미 존재)만 검증, "챌린지 생성 성공/중복"·"피드 생성 성공/중복"·"참가 성공/중복"도 동일 패턴, `PATCH /challenge/2`·`GET /challenge/2`처럼 과거 실행에서 생성된 PK 하드코딩, `DELETE /challenge/5`는 원래 `.expect(200)`이 지금은 `.expect(404)`(이미 삭제됨).
- 즉 생성 계열 엔드포인트의 실제 성공 경로가 사실상 검증되지 않고 있었음.
- 부수 발견: `beforeEach`에서 매 테스트마다 `TestingModule`을 새로 컴파일하고 앱을 새로 띄우는데 `afterAll`(전체 1회)에서만 `app.close()` — 비효율.

### 질문과 결론
- **"격리 전략으로 어느 방향을 원하나요?"** (트랜잭션 롤백 / 별도 DB+truncate·재시딩 / Testcontainers) → **트랜잭션 롤백, 별도 테스트 DB 없이** 기존 로컬 `challenge` DB 그대로 사용하는 걸로 결정. 사이드 프로젝트 규모에 새 DB/env 관리 부담을 지우고 싶지 않다는 이유. (truncate 방식은 개발 데이터가 날아가므로 별도 DB가 필수이고, Testcontainers는 이미 docker-compose로 DB를 운영 중이라 인프라 중복이라는 점도 근거로 제시.)
- **"격리 도입과 함께 죽어있는 성공 assertion도 복원할까요?"** → 둘 다 반영하기로 결정("두개 다 반영해줘라"). 격리가 되면 성공 경로를 실제로 검증할 수 있으므로 이번 스코프에 포함.
- 구현 리스크가 커서(트랜잭션 롤백 트릭이 이 TypeORM/mysql2 조합에서 실제로 동작하는지 검증 필요, 621줄 스펙 전면 재작성) fork에 위임해서 구현 + 반복 검증 + 코드리뷰까지 진행시킴.

## 2. 변경 사항 요약

| 파일 | 변경 내용 |
|---|---|
| `test/utils/transactional-data-source.ts` (신규) | `TransactionalTestDataSource` 클래스 — `getDataSourceToken()` provider를 오버라이드해서, `TypeOrmModule.forFeature()`가 부트스트랩 시점에 싱글턴으로 캡처해버리는 Repository들의 `manager`/`queryRunner`를 매 트랜잭션마다 직접 rebind |
| `test/app.e2e-spec.ts` (전면 재작성, 621→약 700줄) | 별도 테스트 DB 없이 기존 로컬 DB에 대고 트랜잭션 롤백으로 격리. 죽어있던 성공 assertion(회원가입/챌린지/참가/피드의 생성·수정·삭제) 전부 복원, 하드코딩된 PK 전부 "직전 생성 응답에서 받은 id"로 교체 |

**구현 중 겪은 이슈**
- NestJS의 `TypeOrmModule.forFeature()` Repository provider는 부트스트랩 시점에 딱 한 번만 생성되어 `manager`/`queryRunner`를 그 순간 값으로 캡처하는 싱글턴이라, 단순 Proxy 오버라이드로는 트랜잭션을 못 바꿈 — 캐시해둔 Repository 인스턴스들의 `manager`/`queryRunner`를 매 트랜잭션마다 `Object.assign`으로 직접 rebind해야 했음(타입 선언상 `readonly`지만 런타임엔 평범한 프로퍼티).
- **AUTO_INCREMENT 실측**: 롤백해도 InnoDB AUTO_INCREMENT 카운터는 되돌아가지 않음을 직접 확인(`challenge` 테이블 실제 로우 4개인데 다음 AUTO_INCREMENT는 124) — 그래서 하드코딩 PK를 전부 제거하고 매 테스트가 응답에서 받은 id를 쓰도록 설계한 게 맞는 방향이었음.

## 3. 검증 결과

- 로컬 Docker MariaDB(`mariadb` 컨테이너)에 대고 `test:e2e`를 5회 연속 실행 → 매번 53/53 통과.
- 격리 검증: 실행 전후 `user`/`challenge`/`participation`/`feed` 테이블 row count를 직접 쿼리 — 5회 실행 내내 3/4/1/3으로 고정(DB에 흔적이 전혀 안 남음을 확인).
- `npm test`(유닛 10 suites/73 tests) / `npm run build` / `npx tsc --noEmit` 모두 그린.
- `/code-review` 스킬로 diff 리뷰 실행 → 6건 발견, 검증 후 4건 수정 · 2건은 스코프 밖으로 판단:
  1. **수정** — `beginTransaction`/`rollbackTransaction`에 try/finally 없어 실패 시 QueryRunner 누수 가능 → connect/startTransaction 실패 시 즉시 release, rollback은 참조를 먼저 null로 옮긴 뒤 finally에서 release하도록 재작성.
  2. **수정** — rebind가 실제로 먹혔는지 검증하는 코드가 없어 TypeORM 내부 동작에 조용히 의존하고 있었음 → rebind 직후 `repository.manager !== queryRunner.manager`면 즉시 throw하는 방어적 assertion 추가.
  3. **수정** — `createFeed()` 호출이 늘어나면서 디스크에 실제 이미지 파일이 빠르게 누적(실측: 2회 실행 후 85개) → 응답으로 받은 `images` 경로를 추적해서 `afterAll`에서 정확히 그 파일들만 삭제하도록 추가. 재검증 결과 실행당 누적량 17개→2개로 감소(남은 2개는 멀티파트 검증 실패 테스트에서 rejection 전에 디스크에 쓰이는, 응답에 안 잡히는 파일 — 이 프로젝트의 기존 multer 설계 문제라 이번 스코프 밖).
  4. **수정** — `/user/me` 조회 성공 테스트가 원래 `toEqual({id, email})`이었던 걸 `email`만 검사하도록 약화되어 있던 것을 발견 → `toEqual({ id: expect.any(Number), email: SEED_USER.email })`로 정확한 응답 shape 검증 복원(단, id는 하드코딩하지 않음).
  5. **의도적으로 그대로 둠** — 각 describe의 `beforeEach`가 400/401만 검증하는 순수 실패 케이스에도 매번 로그인+fixture 생성을 수행하는 게 비효율적이라는 지적 → describe를 더 잘게 쪼개는 것보다 일관된 구조가 낫다고 판단, 전체 53개 테스트가 5초 내외로 끝나 성능상 문제없음.
  6. **스코프 밖** — `FeedService.getFileArr()`가 근본 원인 대신 호출부에서 증상만 패치했다는 지적 → 이 파일은 오늘 이전 별개 작업(Part 1, 이미 커밋 `9bb2ec1`)이라 이번 e2e 작업에서 손대지 않음.

## 4. 예외 사항 / 남겨둔 것

- `SEED_USER`(`test@gmail.com`)는 로그인 전용 fixture로 로컬 DB에 이미 존재한다고 가정하고 읽기 전용으로만 사용 — 이 계정을 생성/수정하는 테스트는 없음. 로컬 DB를 초기화하면 이 계정을 다시 만들어줘야 함(문서화만 해둠, 자동 시딩은 이번 스코프 밖).
- multer가 rejection 전에 디스크에 먼저 파일을 쓰는 기존 설계 문제(멀티파트 검증 실패 테스트에서 소량의 orphaned 파일이 남음)는 이번 계획 범위 밖으로 기록만 남김.
- `FeedService.getFileArr()`가 항상 배열을 반환하는 근본 원인은 Part 1에서 호출부 증상만 고쳤고 이번에도 그대로 — 필요하면 별도 TODO로 재검토.
- Phase 1-4 남은 두 항목(컨트롤러 계약 테스트, 1-1~1-3 회귀 테스트 보완)은 이번 작업에 포함하지 않음.
