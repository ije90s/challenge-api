# 2026-09-08 작업 기록 — Phase 1-3 마지막 항목: `FeedService.update` 이미지 유실 버그 수정

> `anything/refactor_plan.md` Phase 1-3의 마지막 남은 항목(`FeedService.update`의 이미지 유실 버그)을 처리한 기록. 이 항목 완료로 Phase 1-3(예외 처리/Validation)이 모두 끝나고, 남은 건 Phase 1-4(테스트 보강)뿐이다.

---

## 1. 분석 & 질문

### 분석
- `feed.service.ts:113` (수정 전): `dto.images = this.getFileArr(images) ?? feed.images;`
- `getFileArr()`(`feed.service.ts:20-28`)는 `images`가 `undefined`/`[]`여도 항상 `string[]`을 반환 — `if(images)` 가드 안에서 `.map`하고, 아니면 초기값 `[]` 그대로 리턴. 즉 반환값이 `null`/`undefined`가 될 수 없어 `?? feed.images` fallback은 절대 실행되지 않는 죽은 코드.
- 실제 영향: 사용자가 새 이미지 첨부 없이 제목/내용만 수정하면(`FeedController.updateFeed`의 `FilesInterceptor`가 빈 배열/undefined를 넘김) `dto.images`가 `[]`로 덮어써져 기존 업로드 이미지가 전부 유실됨.
- `feed.service.spec.ts`의 기존 "피드 수정" 테스트(update describe 블록)는 새 이미지를 첨부하는 케이스만 검증하고 있어 이 회귀를 못 잡고 있었음.
- 연관 확인: `UpdateFeedDto`는 `PickType(CreateFeedDto, ['title','content','images'])`이라 `images`는 여전히 `@IsOptional()` — DTO 설계 자체는 문제 없고, 서비스 로직이 "새 이미지 안 왔음"과 "빈 배열로 비우고 싶음"을 구분 못 하는 게 원인.

### 질문과 결론
- **"images 미첨부 시 기존 이미지를 유지하는 걸로 고친다면, '이미지를 전부 지우고 싶다'는 케이스는 이번 스코프에 넣을까요?"** → 넣지 않기로 결정. 새 이미지 없으면 무조건 기존 유지만 처리(스코프 최소화). 전체 삭제 기능은 별도 파라미터/플래그가 필요한 범위 확장이라 이번 버그 수정에서는 제외.
