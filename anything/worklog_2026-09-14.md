### 핵심 발견

1. **filesort 가설 기각**: `EXPLAIN`/`ANALYZE FORMAT=JSON`으로 확인한 결과, `(challenge_id, score, created_at)` 인덱스를 `ORDER BY score DESC, created_at DESC` 쿼리가 InnoDB 역방향 스캔으로 그대로 활용 — filesort 없음. `refactor_plan.md` §1-7에서 실측 전 우려했던 내용은 사실이 아니었음.
2. **진짜 병목 = offset 스캔 비용**: 같은 쿼리를 offset만 바꿔 격리 측정 — offset 0: 0.065ms → offset 40000: 42.8ms. k6 100 VU 부하 시 HTTP p95=1.75s(임계값 500ms 초과), slow query log에 4,582건(전체 요청의 87.5%) 기록.
3. **커넥션 풀 가설 반증**: "TypeORM 기본 풀(10)이 HTTP p95를 DB 쿼리 시간보다 훨씬 부풀린다"는 가설을 세우고 `app.module.ts`에 `extra: { connectionLimit: 100 }`을 임시 추가해 동일 조건 재측정 → p95 1.75s→2.1s, max 2.17s→4.7s, slow 쿼리 8,982건으로 **오히려 악화**. 풀 대기가 아니라 DB 자체의 동시 스캔 처리 한계가 원인임을 확인하고 가설 기각. 코드는 실험 후 diff 없이 원복.

### 시행착오 (중요 — 다음에 비슷한 상황에서 참고할 것)

1. **1차 구현**: `myRank`를 `getChallengeRank` 응답에 합쳐서 반환(합의된 설계대로). k6로 재검증했는데 p95가 거의 그대로(1.75s→1.69s) 나옴.
2. **원인 조사 1단계**: `kill %1`/`pkill -f "nest start"`가 실제로는 프로세스를 못 죽이고 있었음 — Bash 도구 호출마다 새 쉘이라 job control(`%1`)이 안 먹히고, `pkill -f`의 패턴이 실제 실행 커맨드(`node .../dist/src/main`)와 안 맞았음. PID를 `lsof -ti :3000`으로 직접 찾아 `kill -9`로 죽여야 확실했음. 이 문제로 "재검증"이라고 생각한 실행 중 상당수가 실제로는 고치기 전 서버를 때리고 있었다.
3. **원인 조사 2단계**: PID를 직접 죽이고 진짜 고쳐진 코드로 재검증해도 여전히 개선 없음(오히려 p95 2.82~3.85s로 악화, 반복할수록 더 나빠짐). slow query log를 보니 `myRank` 쿼리 자체가 버그로 **챌린지 필터가 깨져 테이블 전체(10만 건)를 스캔**하고 있었음(`.andWhere()`에 넘긴 OR 조건을 전체를 감싸는 괄호 없이 작성한 게 원인) — 수정.
4. **원인 조사 3단계**: 괄호 버그를 고치고 Docker 컨테이너까지 재시작해서 완전히 깨끗한 환경에서 재검증했는데도 여전히 개선이 미미(p95 2.82s). `myRank`가 이제 모든 요청마다 COUNT 쿼리를 하나 더 무는데, 격리 상태에선 6.5ms로 싸지만 100명 동시 요청 하에서는 경합 때문에 50~60ms로 늘어나 — offset 문제를 고친 대신 "모든 요청에 새 비용을 얹은" 셈이 됨. 이걸 `AskUserQuestion`으로 다시 확인 → **myRank를 별도 엔드포인트로 분리**하기로 재결정(1번 질문의 답을 뒤집음).
5. **분리 후 완전히 깨끗한 환경(컨테이너 재시작 + 재시딩 + 새 서버 프로세스)에서 최종 검증**: p95 1.75s→**473ms**(임계값 500ms 통과), 처리량 52.4→**189.3 req/s**.

### 구현 중 발견해서 함께 고친 버그

- `myRank` 쿼리의 OR 조건 괄호 누락 → 챌린지 필터 우회, 테이블 전체 스캔 (위 시행착오 3단계)
- `Participation.created_at`이 DB엔 `timestamp(6)`(마이크로초)인데 Entity(`@CreateDateColumn`)엔 정밀도 미지정 → JS Date 왕복 시 정밀도 손실로 **자기 자신을 자신보다 높은 순위로 잘못 카운트**하는 off-by-one 버그. e2e 테스트("내 순위 조회 › 조회 성공", 참가자 1명뿐인 챌린지에서 myRank가 1이 아니라 2로 나옴)로 발견. `p.id != :myId` 조건으로 자기 자신을 명시적으로 제외해서 수정.
- `anything/loadtest/seed_participation.py`: `NOW(6)`이 SQL 문 단위로 한 번만 평가되어 1000행 배치마다 `created_at`이 동일해지는 문제(이전 TODO에서 발견) — 행마다 마이크로초 단위로 다른 타임스탬프를 Python에서 직접 생성하도록 수정.
- `anything/loadtest/setup_users.sh`: `$TOKEN`을 python 문자열에 직접 삽입하던 걸 환경변수 전달로 교체(코드리뷰 지적, 토큰에 특수문자가 섞이면 스크립트가 깨지거나 조용히 데이터가 손상될 수 있었음).
