## 1. 분석 & 질문

### 분석

- 대상 엔드포인트(`ChallengeController.findAll/findOne`, `FeedController.findAll/findOne`)의 서비스 메서드(`ChallengeService.findAll/findOneById`, `FeedService.findAll/findOneById`)를 확인한 결과, 어디에도 `user`를 파라미터로도 받지 않음 — 즉 현재 걸려 있는 클래스 단위 `JwtAuthGuard`는 기술적으로는 불필요, 순수하게 정책적 선택.
- `UserController`는 이미 클래스 단위가 아니라 `GET /user/me`에만 `@UseGuards(JwtAuthGuard)`를 개별 적용하는 패턴을 쓰고 있어, "일부만 공개"로 갈 경우 참고할 선례가 존재함을 확인.
- `ParticipationController`는 범위 밖 — `getChallengeRank`/`getMyChallenge` 등 전 라우트가 `user.id`를 실제 비즈니스 로직(본인 참가 여부 확인)에 사용하므로 애초에 조회도 인증이 필요함.
- e2e(`test/app.e2e-spec.ts`)에는 이 4개 GET 라우트에 대한 401 케이스가 없어, Guard를 풀어도 기존 실패 케이스는 깨지지 않는다는 것도 확인(참고용, 결과적으로 미사용).

### 질문과 결론

- **"조회 엔드포인트 공개로 전환할까요, optional auth를 도입할까요, 현행 유지할까요?"** → 처음엔 작성자가 "챌린지 생성/참여는 로그인 필요"라는 의도만 설명해서 공개 전환(쓰기만 막고 조회는 열기)을 권장했으나, **"조회도 볼 수 없게 막았다"** — 즉 회원가입 안 된 유저는 조회를 포함해 전혀 접근하지 못하게 하는 것이 애초 의도된 정책이었음을 확인.
- **결론**: 현행 클래스 단위 `JwtAuthGuard` 유지. 코드 변경 없음 — 분석 결과 기술적으로는 불필요하지만, 의도된 정책이므로 그대로 둔다.

## 2. `forwardRef` 순환 의존 재검토

### 분석

- `UserModule`이 `AuthModule`을 import하는 이유는 단 하나 — `UserController`가 로그인(`POST /user/login`) 처리를 위해 `AuthService`를 주입받기 때문(`user.controller.ts`). `UserService`는 `AuthModule`/`AuthService`를 전혀 참조하지 않음.
- 반대로 `AuthModule`이 `UserModule`을 import하는 건 실제 필요한 의존 — `AuthService`와 `JwtStrategy` 둘 다 `UserService`를 주입받아 씀.
- 즉 진짜 필요한 의존은 `AuthModule → UserModule` 단방향뿐이고, `UserModule → AuthModule`은 "로그인 라우트가 `UserController` 안에 얹혀 있다"는 배치 때문에 생긴 부산물.
- `UserController`는 이미 클래스 단위 Guard 없이 라우트별로 공개/비공개를 나누고 있어(`signUp`/`signIn`은 공개, `fineOne`만 Guard) 참고할 선례가 있음을 확인.
- 해결책으로 로그인 라우트를 `AuthModule` 소속의 새 `AuthController`(`@Controller('user')`로 경로 그대로 유지)로 옮기는 방안을 분석 — `forwardRef` 양쪽 다 제거되고 API 경로/e2e 변경 없음을 확인.

### 질문과 결론

- **"컨트롤러를 인증 관심사(Auth)와 리소스 관심사(User)로 분리할까요?"** → 작성자 원칙 확인: "서비스단에서 처리한다고 생각해서 컨트롤러를 따로 안 만들었다, 컨트롤러는 외부 통신 제어용"이라는 설계 의도였음. 실제로 로그인 로직은 이미 전부 `AuthService`에 있고 `UserController.signIn()`은 얇은 라우팅 계층뿐이라 원칙 자체는 지켜지고 있는 상태.
- **결론**: "로컬 단에서 부하 테스트까지만 진행하고 보안은 강하게 하지 않기로 했다"는 프로젝트 방침(`anything/refactor_plan.md` §8 참고) 하에서는 이 리팩토링의 실익이 낮다고 판단 — **현행 구조(양쪽 `forwardRef`) 유지**. `forwardRef`는 NestJS가 공식 지원하는 정상 패턴이라 "고쳐야 하는 버그"는 아님. 코드 변경 없음.
