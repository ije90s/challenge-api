# 2026-09-05 작업 기록 — Phase 1-1 `noImplicitAny` 전환

> `anything/refactor_plan.md` Phase 1-1의 첫 세 항목(타입 강화)을 진행한 기록.

---

## 1. 분석 & 질문

### 분석
- `tsconfig.json`을 직접 건드리지 않고 `npx tsc --noEmit --noImplicitAny -p tsconfig.json`으로 오버라이드해서 실제 컴파일 에러를 먼저 뽑아봄 (`test/app.e2e-spec.ts`를 포함한 전체 프로젝트가 컴파일 대상에 들어가는 것도 확인).
- 결과: 에러 12개, 전부 `@User()` 데코레이터 파라미터(`challenge.controller.ts` 3곳, `feed.controller.ts` 3곳, `participation.controller.ts` 5곳, `user.controller.ts` 1곳). 다른 곳(서비스/필터/인터셉터/미들웨어/테스트)에는 암묵적 `any` 없음.
- 원인: `common/user.decorator.ts`는 `createParamDecorator`로 만든 커스텀 파라미터 데코레이터라 TS가 반환 타입을 호출부로 전파해줄 방법이 없음 — NestJS 공식 문서 패턴 자체가 사용하는 쪽(`@User() user: X`)에서 타입을 직접 명시하는 구조.
- 런타임 확인: `JwtStrategy.validate()`가 `userService.findOneByEmail(email)`(`await` 누락, 별도 버그로 계획서에 이미 기록됨)을 리턴 → async 함수라 Promise가 자동 언래핑되어 `request.user`에는 `User` 엔티티 전체(`password` 해시 포함)가 들어감. 하지만 12곳 호출부 전부 `user.id`만 사용하고, 이 값을 넘겨받는 서비스 메서드도 전부 `userId: number` 하나만 받음.

### 진행 중 나온 질문과 결론
- **"RequestUser에 email은 왜 넣었나?"** → 실사용처가 없어서 제외. 초기 제안(`{ id: number; email: string }`)은 근거 없는 추측성 설계였음 — 최종적으로 `{ id: number }`만 정의.
- **"이것도 DTO 아닌가?"** → 아니다. 이 프로젝트의 `Dto`는 (1) 클라이언트 요청 바디 검증(`Create/Update*Dto`, class-validator) 또는 (2) 응답 바디 매핑(`Response*Dto`, 민감 필드 제거)을 위한 것. `RequestUser`는 이미 JWT 인증을 통과해 신뢰된 값이 서버 내부에서만 도는 것이라 검증/매핑 로직이 필요 없고, 컴파일타임 계약만 있으면 되는 `type`으로 충분함.
- **"도메인별은 dto 폴더, 공유되는 건 common 폴더가 맞나?"** → 맞음. 이 저장소에 이미 같은 논리의 선례 존재 — `common/dto/request-query.dto.ts`, `common/dto/response-paging.dto.ts`도 여러 도메인이 공유해서 `common/dto`에 있음. `RequestUser`/`JwtPayload`도 여러 도메인이 공유하므로 `common`에 두되, DTO가 아니라 type이므로 `common/dto`가 아닌 새 하위 폴더 `common/types`로 구분.
- **(코드 리뷰에서 나왔다가 철회된 지적) "데코레이터 팩토리에 리턴 타입을 상세히 적으면 호출부 타입 불일치를 컴파일러가 잡아주지 않나?"** → 실험으로 반증함. 팩토리 콜백에 `: RequestUser` 리턴 타입을 지정해도, 호출부에 일부러 틀린 타입(`{ wrongField: string }`)을 달아도 컴파일 에러가 안 남 — TypeScript의 파라미터 데코레이터(`ParameterDecorator`)는 런타임 메타데이터 등록용일 뿐 데코레이션 대상의 타입을 검사/추론하지 않기 때문. 따라서 현재 방식(호출부마다 어노테이션)이 구조적으로 최선이라는 결론.

## 4. 예외 사항 / 사고

- **`npm run format` 오사용 사고**: 코드 리뷰에서 나온 "신규 파일 들여쓰기" 지적을 고치려고 `npm run format`을 실행했는데, 이 스크립트가 `prettier --write "src/**/*.ts" "test/**/*.ts"`로 전체 glob을 대상으로 해서 **관련 없는 51개 파일이 통째로 재포맷**됨 (기존 코드가 4-space였는데 `.prettierrc`에 `tabWidth` 설정이 없어 prettier 기본값인 2-space로 전부 바뀜).
  - 사용자가 "51개 파일 한꺼번에 변경하는 거 별로다"라고 해서 `git checkout --`으로 전부 되돌리고, 의도했던 변경(4개 컨트롤러 + `tsconfig.json`)만 다시 적용 → `npx prettier --write <단일 파일>`로 신규 파일만 재포맷.
  - 재발 방지를 위해 "이 저장소에서는 `npm run format`(전체 glob) 대신 항상 `npx prettier --write <파일>`로 범위를 좁힐 것"을 메모리에 저장함 (`feedback_prettier_scope`).
- **범위 밖으로 남겨둔 것** (Phase 1-1 잔여 항목 및 인접 이슈, 이번에 손대지 않음):
  - `JwtPayload` 타입 정의 및 `sub`(string) vs 실제 `user.id`(number) 불일치 수정 — 다음 작업 대상
  - `JwtStrategy.validate()`의 `await` 누락 버그 — Phase 1-3 대상
  - `request.user`가 실제로는 `password` 필드까지 포함한 `User` 엔티티 전체라는 점 — `RequestUser` 타입을 좁게 정의해도 런타임 객체 자체가 좁아지는 건 아님. 지금은 문제 없지만 인지하고 있을 것.
